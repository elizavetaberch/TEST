# Git workflow

## Правила команды

- ветка на тикет: `KES-16-akkordeon`
- коммит: `[TASK] KES-xx Описание` — английский, повелительное наклонение (`Add`, `Fix`, `Remove`)
- **merge, не rebase**: `git fetch origin && git merge origin/main`
- push только в свою ветку: `git push -u origin <branch>`
- PR создаётся в Bitbucket
- ❌ никогда: `git push origin HEAD:main`, `--force`, `-f`

> [!danger] Уже ошибался
> Один раз запушил в main напрямую, минуя PR. Ничего не затёр, но правильно было честно написать Бенни «забыл про PR», а не придумывать оправдание.

## Три зоны

1. **Рабочая папка** — файлы на диске
2. **Индекс (staging)** — корзина для следующего коммита
3. **Репозиторий** — история

`git add` копирует из 1 в 2. `git commit` превращает 2 в коммит.

> [!tip] Главное про add
> `git add` фотографирует файл **в момент вызова**. Изменил файл после `add` — делай `add` ещё раз. Иначе закоммитится старая версия.
> Файл может быть одновременно в обоих списках `git status` — это оно и есть.

## Команды

```bash
git status
git add -A            # весь репозиторий, из корня проекта
git add .             # только текущая папка и ниже ← так теряют файлы
git add -u            # только отслеживаемые

git diff              # что на диске, но не в индексе
git diff --staged     # что уйдёт в коммит
git --no-pager diff --staged   # без пейджера

git commit -m "..."
git commit --amend -m "..."    # переписать последний коммит
git log --oneline -3
```

> [!warning] amend
> Только до push. После push — нельзя, история разойдётся у всех.

## Навигация в less

| Клавиша | Действие |
|---|---|
| `Space` / `b` | страница вниз / вверх |
| `j` / `k` | строка вниз / вверх |
| `g` / `G` | в начало / в конец |
| `/текст` | поиск, `n` — следующее |
| `q` | выход |

## Чтение diff

- `@@ -10,9 +10,11 @@` — в старом файле с 10-й строки 9 строк, в новом 11
- `-` красное = было, `+` зелёное = стало, без знака = контекст
